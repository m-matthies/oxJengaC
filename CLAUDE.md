# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

oxJenga is an interactive AR/VR (WebXR) simulation of DNA/RNA nanostructures. A structure is rendered with three.js, simulated live by a remote oxDNA instance (oxServe), and users pull nucleotides with XR controllers. This repo (`m-matthies/oxJengaC`) is a standalone copy of `Akodiat/oxJenga`; the `upstream` remote points there. It is deployed via GitHub Pages at https://m-matthies.github.io/oxJengaC/.

## Running and linting

The app is built with Vite. There is no test suite.

- `npm run dev`: dev server (`--host`, so headsets on the LAN can reach it).
- `npm run dev:https`: the same over HTTPS with a self-signed certificate (`@vitejs/plugin-basic-ssl`, enabled by `--mode https` in `vite.config.js`). Use it for headsets, because WebXR needs a secure origin; accept the certificate warning once in the headset browser.
- `npm run build` → `dist/` (git-ignored). `npm run preview` serves the build.
- `npm run deploy`: builds, then pushes `dist/` to the `gh-pages` branch of `origin` (the `gh-pages` package). GitHub Pages serves that branch, so the site updates a minute or so later.
- `npm run lint`: ESLint 8 with the legacy `.eslintrc`. Style rules: 4-space indent (`case` at the same indent as `switch`), double quotes, semicolons, unix line endings.
- three.js is an npm dependency pinned to 0.186.1; addons are imported as `three/addons/...`.
- `vite.config.js` uses `base: "./"`, so the build works under any path (e.g. GitHub Pages `/oxJenga/`). Static files live in `public/` and are referenced at runtime through `import.meta.env.BASE_URL`.

## Architecture

**Data flow:** `.oxview` JSON → `System` model → oxDNA top/dat strings → oxServe WebSocket → streamed dat frames → interpolated instanced mesh.

- `main.js`: owns all scene state as module-level globals (`scene`, `group`, `system`, `ox_socket`, `forces`). It contains `initSceneFromJSON` (parses oxView JSON into the model and opens the socket), the XR controller handlers (`onSelectStart`/`onSelectEnd`), hover highlighting with haptics (only while `renderer.xr.isPresenting`), and the `render()` animation loop (registered once with `setAnimationLoop`).
- `src/system.js`: `System` → `Strand` → `Monomer` (abstract), with subclasses `DNAMonomer`, `RNAMonomer` and `AminoAcidMonomer`. These differ only in `getBackboneOffset()` (the backbone offset from the centre along a1/a2) and `getCategory()`. `System` also owns the whole view side: `createViewMesh()`, `setTargetsFromDat()`, `updateView()`, `pick()` and `setHighlighted()`. **Everything on the view/simulation side uses the element `index`, not the oxView `id`** (see below).
- `src/file.js`: `makeTopFile`/`makeDatFile` (old-style oxDNA topology and configuration) and `updateStrandsFromDat`, which just calls `system.setTargetsFromDat`.
- `src/oxserve.js`: `OXServeSocket` (a `WebSocket` subclass) connecting to `wss://nanobase.org:8989`. Incoming messages (around 5 MB per frame for flippy) are forwarded unparsed to `src/datWorker.js`. The worker runs `JSON.parse` and the dat parsing (`src/datParser.js`, shared with the main thread's `setTargetsFromDat` for dropped files) and transfers a `Float32Array` of targets back. The main thread copies it in with `system.setTargets()` and hands the array back to the worker for reuse. It sends JSON `{settings, top_file, dat_file[, trap_file]}` and sends the string `"abort"` to stop. It receives `{console_log}` and `{dat_file}` messages. `start_simulation` waits for the socket to open if it is still connecting, and includes the current trap file if there is one. Forces, a dropped dat, Reset structure and Reconnect all restart through `restartSimulation(dat, forces)` in `main.js`. It shuts the socket down and opens a fresh one only once the old one has closed (at most `RESTART_CLOSE_WAIT`, 1 s, so oxServe never counts both against its connection limit; a restart requested meanwhile replaces the pending one). It does this because a restart on the same socket (`update_forces`/`load_dat` with `"abort"`) receives late frames from the killed run, and showing them makes the structure snap back when the new run starts from `dat`. `connect()` calls `system.resetFrameTiming()`, so the restart gap is not taken as a frame interval.
- `src/relax_scenarios.js`: oxDNA input settings for DNA2 and RNA2 (CUDA MD). The scenario is chosen from the category of the first monomer. Amino acids (`AA`) have no scenario: the constructor warns and returns early.

### Invariants that span files

- **Neighbour links:** some exports list only `n3` per nucleotide (no or only some `n5`, no `bp`, e.g. flappy). `initSceneFromJSON` completes each link from the other side before `assignIndices()`, otherwise the topology would get no 5′ neighbours.
- **Ids vs indices:** oxView ids can be sparse and in any order (flippy's 19,159 nucleotides have ids up to 31041), so they are only used to look up elements while loading (`system.elements`). `System.assignIndices()` must run after loading and before `createViewMesh()`/`makeTopFile()`. It gives each element a dense `index` in oxDNA order: strand by strand, each strand reversed from oxView's 5'→3' order to 3'→5'. That index is the line in the top/dat files, the topology's neighbour references, the oxDNA particle index of trap forces, the mesh instance index, and the position in `system.monomersByIndex`. `pick()` returns it as `hit.index`. Topology strand numbers are the strand's position in `system.strands` + 1. Circular strands (such as flippy's scaffold) work because neighbours are explicit indices.
- **View state lives in typed arrays, not on `Monomer`s.** After `createViewMesh()`, `Monomer.position`/`a1`/`a3` hold the *initial* structure (used for the top/dat sent to oxServe) and are never updated. The displayed backbone positions are the translation part (offset 12) of each 16-float matrix in `instancedMesh.instanceMatrix.array`. `system.targets` (3 floats per index) holds the latest frame's backbone positions. The instance count is the number of elements.
- **Hot paths avoid allocation:** `parseDatTargets` (in `datParser.js`) parses numbers straight from the string's character codes (no `split`, no substrings). It computes the backbone position from the frame's own a1/a3. `updateView` moves each bead linearly in time toward its target over `LERP_OVERSHOOT` (2) × the moving-average frame interval. oxServe frames come irregularly, and 2× trades fewer pauses for some lag. A visual thermal noise during pauses was tried and dropped; don't add it back. It does nothing once settled, and it refreshes the bounding sphere used for frustum culling. `pick` is an analytical ray–sphere test on the bead centres; it replaces three's per-instance `InstancedMesh.raycast`. Hover colour changes upload only the affected instance via `addUpdateRange`. Keep new per-frame code in this style: module-level scratch objects, no `new` inside `render()`.
- **Coordinate spaces:** the oxDNA coordinates live in the local space of `system.instancedMesh`, which is offset by `-box/2` and sits inside `group`. `group` is scaled to `targetScale` (1/100) and stays at that scale. There is no zoom-in animation: it was removed because it skewed pull targets during the first seconds. Controller positions are turned into trap targets with `system.instancedMesh.worldToLocal`.
- **Forces:** `forces` is a `Map` from controller to `{nucId, particles, offsets, stiff, target, oxDNATarget}`; `startPull()` creates one and `sendForces()` turns all of them into the trap file. A pull acts on every bead whose latest backbone position is within `PULL_RADIUS` (5.2 oxDNA units, a bit over a six-helix bundle's radius) of the picked bead (`system.getIndicesWithin`). Each bead gets its own `type = trap` block. They share `pullStiffness` (the total stiffness: 0.15 by default, chosen in the menu from `STIFFNESS_STEPS` and remembered in `localStorage`), so each gets `pullStiffness / N` and the region is pulled gently as a whole. This is deliberate. Full per-bead stiffness, as in the original single-bead pull, was tried: it yanks the region out to the target within one frame, which the user found too violent. **Trap `pos0` must be built from centres of mass, not backbone sites:** oxDNA applies traps to particle positions (the COM), which are about 0.48 units from the drawn backbone sites. `startPull` reads the COMs with `readPositions()` (`src/datParser.js`) from `ox_socket.get_latest_dat()`, the same frame the restart then sends. The picked bead's COM goes to the target, and the others keep their COM offsets from it. The target is the controller position when the trigger was pressed; the pull stays after release until that controller selects empty space. Moving the target while the trigger is held was tried and dropped: every trap change restarts the oxServe run, which is too slow to follow a hand. Each controller has one reusable "tractor beam" cone (`userData.cone`) and a wireframe sphere (`userData.sphere`) that shows the pull region while hovering or pulling. Both are repositioned every frame.
- **Menu (move mode):** X/Y on the left controller (by `inputSource.handedness`; also any gamepad button index ≥ 7, where some runtimes report the menu button) toggles `moveMode`. With hands, any button after 1 on the left hand's emulated gamepad toggles it (0 is the pinch; 1 may be squeeze, i.e. a grasp). Quest normally keeps the left-palm pinch gesture for its own menu, so `onSessionVisibilityChange` also opens our menu when the session comes back from being blurred or hidden while the left input is a hand. A floating palm button was tried and removed, because it clashed with Quest's own palm icon. `MovePanel` (`src/movePanel.js`) is a canvas-textured plane: it is attached to the left controller, or placed in the room in front of the viewer when the left input is a hand. `placeMenu()` does this, again on session start and whenever the inputs switch between hands and controllers (`menuNeedsPlacement`). Its buttons are:
  - Structure selection (see Designs).
  - Reset position.
  - Reset structure: reloads `initialDat`, the starting configuration, into the view and oxServe without pulls, in one restart.
  - Stiffness −/+.
  - Reconnect: shuts the socket down and calls `connect()` with the latest dat and the current forces.
  - Hide/Show box: toggles `boxHelpers`, the box and axes, and is remembered in `localStorage`.
  - Done: closes the menu; if the stiffness was changed, it also applies to active pulls (one restart).
  - Exit XR: ends the session. With hands, Quest's own quit needs a short right-palm pinch, which easily becomes a recenter. They are hit by ray + select (`hitTest`) or by poking with a finger tip or controller (`poke`). `menuAction()` runs them. While the menu is open, select grabs `group`: `grab.offset` is the group's pose relative to `grabFrame()` (the controller pose, or for a hand the pinch point turning with the wrist), which `updateGrab()` reapplies every frame (position and rotation only; the scale stays fixed). Opening it does not touch the simulation: pulls stay. Their targets are in oxDNA coordinates, so they move with the structure, and `updateCones()` draws each cone from `localToWorld(oxDNATarget)`.
- **Hands:** the `hand-tracking` optional feature is requested. `renderer.xr.getHand(i)` (with mesh hand models) is stored as `controller.userData.hand`. A hand shares its controller's select events (a pinch is a select), so `isHand(controller)` switches behaviour. A pinch within `HAND_REACH` (3 cm) of a bead (`system.nearestDisplayed`) selects directly. The region is dragged (cone from the pinch point) and, when the pinch opens, pulled toward that point: one restart per gesture. Hands have no pointing ray (a shoulder-to-knuckle ray was tried and felt counterintuitive): a pinch with no bead in reach releases that hand's pull. In the menu, hands only poke. `updateHands()` shows each hand mesh only while its wrist is tracked, so untracked hands don't leave frozen meshes behind.
- **oxServe server:** its source is in `~/Data/fix_serve/prod-ox-serve` (`main.js`/`server.ts`); the copy there may differ from what runs on nanobase.org. Every message kills the running oxDNA process. A JSON message then writes `conf_file.dat` *and* `last_conf.dat` = our `dat_file`, so the new run's first frame repeats the starting configuration. Only if `trap_file` is present does it write `trap.txt` and set `external_forces`; settings keys ending in `_file` etc. are dropped. A frame (`last_conf.dat` + `console_log`) is sent on every oxDNA stdout chunk, so a killed run can still send late frames. Connections beyond `allowed_connections` are closed when they arrive; existing ones aren't dropped.
- **Dev hook:** under `npm run dev` only, `window.__oxjenga` exposes `system`, `socket`, `group`, `forces`, `startPull`, `sendForces` and `releasePull` for headless tests (it is stripped from builds).
- **oxServe connection:** `connect(dat, forces)` opens the socket and starts the run. A connection lost unintentionally (`intentionalClose` is set by `shutdown()`) is re-established from `get_latest_dat()` with the same forces, after 2 s and at most 3 times a minute, and only while the page is visible. Otherwise `sendForces()` and Reset structure reconnect on demand. The oxServe server may allow only one client at a time, so a second page or test client can drop the headset's connection. While the menu is open, `updateConnectionStatus()` shows the live connection state next to Reconnect: Connecting, Starting (run not yet producing frames), Running, No frames (none for 20 s, using `lastFrameAt`) or Disconnected. The bottom line shows the room-anchor state.
- **Run start latency:** each (re)start (every new or released pull) makes oxServe start a new run, which takes about 10-20 s for flippy. A fresh connection or a start without abort is no faster. Until then the aborted run may still send frames. `OXServeSocket.starting` is set from `start_simulation()` until a frame arrives whose header (`t = ...`, read by `frameHeader()` without parsing the message) equals the header of the dat the run was started from. Use `isStarting(now)`, which also expires after 60 s and is cleared when the socket closes. It is only an indicator: all frames are applied, including late ones from the aborted run. Dropping those was tried and felt less smooth, so don't drop them. After 60 s the run stops counting as starting. `updateStartingLabel()` shows "Starting simulation… N s" above the structure meanwhile.
- **Session end keeps state:** leaving the XR session (e.g. for the system menu) keeps the pulls, the open menu and the placement. `stopInteractions()` only ends what needs a held trigger or pinch (grab, drag, highlights), also while the session is blurred.
- **Room anchoring:** `RoomAnchor` (`src/roomAnchor.js`) keeps `group` fixed in the real room across headset recentering (e.g. taking the headset off and on). It ties the group's pose to a WebXR anchor (the `anchors` optional feature) that is applied every XR frame, except while the group is grabbed or while a new anchor is pending. Releasing a grab or pressing Reset calls `requestPlacement()`. If there is no saved placement (first start, or the restore failed), `onInitialPose` puts the structure in front of the viewer first (`placeInFrontOf` in `main.js`: its bounding radius + 0.75 m ahead, 0.2 m below eye level, turned to face the viewer), so it never starts in the viewer's face. Reset position does the same. Old persisted handles (`staleHandles`) are only deleted once the new placement is saved. Where the browser supports it (Quest Browser), the anchor is persisted and its handle kept in `localStorage`, so the placement also survives new sessions. Quest allows a site only 8 persistent anchors, so none may leak:
  - A replaced anchor's handle is deleted.
  - So is a handle that resolves after its anchor was superseded, and one that fails to restore.
  - At session start, persisted anchors other than the stored one are deleted.
  - A failed save frees all the others and retries. Without anchor support it falls back to undoing the reference space's `reset` transform.
- **Lighting:** a `RoomEnvironment` PMREM (`scene.environment`, intensity 0.3), a hemisphere light, a shadow-casting key light that follows `group` (so its ±1 m shadow camera covers the structure wherever it is placed), plus fill and rim lights, and `NeutralToneMapping`. The bead material is matte (roughness 0.85, metalness 0). When AR light estimation ends, `scene.environment` is restored to the room environment.

### Designs

The `.oxview` files live in `public/resources/`. The loadable set is `DESIGNS` in `main.js` (`{file, name}`): currently flappy (`flappy.oxview`, 18,888 nt, 270 strands, the default), flippy (`flippy_turned.oxview`) and monohole (`monohole_1b.oxview`). The first entry is the default. `DESIGN_KEY` is renamed whenever the default changes, so that the new default is loaded once even where an older choice was stored. The other files stay in `public/resources/`. The menu's ◀ ▶ buttons choose a structure, and Load structure calls `loadDesign()`. That function fetches the file and runs `initSceneFromJSON`, which shuts down the old socket and system only after the new design has parsed. `designLoadId` makes sure only the last requested load is shown. The last loaded design is stored in `localStorage` and loaded on startup; by default that is the first entry. Don't list `1eua.oxview`: it is protein (`AA`), which has no relax scenario. The box in each `.oxview` file is what gets simulated and drawn: both flippy files were set to 250 (the originals were 5000). To add a design, put the file in `public/resources/` and add it to `DESIGNS`. Dropping a `.dat` file onto the page updates the current positions.
